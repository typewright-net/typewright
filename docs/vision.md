I want to start building a new project called `Typewright` that will consistent of several distinct components:

- A DDD model validation framework for .NET that uses readonly record struct types for each field in a domain model, having those types enforce invariants so creating invalid data is not possible.
- An ASP.NET middleware (or similar) built on the first to allow HTTP endpoints and other interfaces to directly define request parameters in terms of these validated domain model types and automatically apply the validation rules before invoking the endpoint, returning 400-level errors with the domain validation failures if any data is invalid, before ever entering the endpoint code.
- A local, actor-style framework for processing messages, basically F# MailboxProcessor but for C# and with some increased capabilities in terms of providing modular components like the mailbox itself (e.g. IMailbox) that can be replaced with user-defined implementations.  The intent would not necessarily be to build a full-scale Actor framework like Akka.NET with clustering and myriad other features, but perhaps having a few framework-provided actors to simplify specific use-cases not handled by F# MailboxProcessor, like getting two sets of local actors on different servers to communicate, by having a communication actor that exchanges messages with the other system over a normal protocol like HTTP.
- An in-memory object/data-structure server (codename Lattice), similar to Redis but with built-in object support so the data at a given key is always strongly typed (even supporting the domain models from the first framework for something akin to field-level schema validation) and a graph of objects can be traversed and queried via LINQ against the in-memory data-structure server.   This would utilize the Actor framework such that an agent handles all commands for each resource,  serializing the operations at a per-key level while allowing operations on different keys to execute in parallel without blocking each other.  Actors can be sharded across nodes based on a consistent hash of the resource path, and an append-only data stream allows for the in-memory data to be persisted/re-loaded.
- A RESTful document database built on all of the above where using a standard HTTP Verb like GET, POST, PUT, PATCH, or DELETE with a specific resource path routes the request to agent handling the key that corresponds to the resource URI.  Data is automatically validated by the validation framework so only valid data for the domain model is sent to the data layer.  The idea would be that by putting enough thought into the Domain Model and representing that in the data types, you would basically get a CRUD API for it automatically.
